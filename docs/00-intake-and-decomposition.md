## 二、立项评估（Intake Assessment）

### 2.1 一个必须先说清楚的残酷前提

短视频赛道**不是蓝海，甚至不是红海，是血海**。

| 事实 | 数据 | 含义 |
|---|---|---|
| 中国短视频用户规模 | 10.74 亿，渗透率 95.4%，年增速仅 0.8% | 增量市场已终结 |
| 头部集中度 | 抖音 MAU 约 10 亿、快手 DAU 4.16 亿、视频号 DAU 约 5 亿 | 前三名占据绝大部分注意力 |
| 推荐机制门槛 | 头部平台已实现召回—粗排—精排—重排四段式 + 千亿级特征 | 算法起跑线极高 |

**结论：如果本项目的立项假设是"做一个更好的抖音"，那么答案是不要做。** 任何新平台都无法在通用短视频赛道用同等资源正面竞争。

### 2.2 那什么路径还能成立？三个可行切口

基于竞品调研（`01`）与用户调研（`02`）的交叉验证，只有三个切口在逻辑上成立：

| 切口 | 论证依据 | 代价 |
|---|---|---|
| **A. 垂直品类深耕**（美食/宠物/健身等单垂类） | 通用平台的长尾垂类创作者拿不到确定性流量；用户调研显示 50-59 岁新银发人群（占 20.9%，行业唯一增量）与轻创作者在两端的痛点最集中 | 天花板低，需靠垂类做到足够深再横向扩张 |
| **B. 创作者侧确定性供给**（保底曝光 + 即时反馈 + 透明数据） | 用户旅程情绪断崖集中在「首次发布 → 首次收到反馈」；存量竞争下胜负手在供给侧而非需求侧 | 需要补贴或机制设计，早期成本高 |
| **C. 私域/关系链冷启动**（类似视频号的社交分发） | 视频号用社交关系链绕开了与抖音的算法正面比拼，证明分发路径本身可以差异化 | 依赖既有关系链资产，从零起盘不可复制 |

**本次 MVP 的技术选型服务于 A 与 B**：推荐算法特意把「内容标签匹配」与「创作者打散」做成一等公民而非补充模块（详见 `03`），因为垂直品类 + 创作者扶持场景下，协同过滤天然稀疏、必须靠内容理解与流量公平性兜底。

### 2.3 立项决策建议

| 决策项 | 建议 | 理由 |
|---|---|---|
| 是否立项 | **有条件立项**：仅当确认垂直切口（A 或 B）后立项 | 通用赛道不可进入 |
| MVP 范围 | 视频上传 + 推荐流（本次已交付） | 需求明文指定，且是"创作者发得出、用户看得下去"的最小闭环 |
| 明确不做 | 直播、IM 私信、电商、算法 DNN 化 | 无行为数据前，DNN 是负收益；先要可解释的基线 |
| 北极星指标 | 创作者次周留存 × 人均有效观看时长 | 单看 DAU 会掩盖"只有消费没有供给"的空心化 |

## 五、本次交付的核心工程决策（含 Trade-off）

| 决策 | 选择 | 被否决的方案 | Trade-off |
|---|---|---|---|
| 技术栈 | Python 标准库（`http.server` + `sqlite3`） | Flask/FastAPI 全家桶 | 换取**零依赖可运行性**（目标环境无 pip 包），代价是需自研 multipart 解析与路由 |
| 上传解析 | 自研流式 boundary 扫描 | `email` 解析器一把梭 | 换取**内存安全**（200MB 上限下驻留 ≤64KB），代价是约 120 行边界代码与更严格的测试 |
| 元数据真值 | ffprobe 服务端探测 | 信任客户端上报 | 换取**风控正确性**（防 3 秒视频冒充 3 分钟），代价是依赖 ffmpeg |
| 排序模型 | 线性加权（可手算） | 直接上 DNN 双塔 | 换取**可解释性与零数据依赖**，代价是表达能力上限低 |
| 冷启动 | 标签匹配 + 分垂类热门为主 | 协同过滤为主 | 换取**稀疏行为下的可用性**，代价是早期个性化精度有限 |
| 多样性 | MMR + 创作者打散（硬上限 2 条） | 纯相关性排序 | 换取**长期留存与创作者公平**，代价是短期点击率略降 |

### 线上实测（真实起服务 + 6 条真实 mp4 + 239 条行为）

```
请求: GET /api/feed?user_id=<新用户>&size=5
（该用户点赞了一条"美食"视频、看过一条"宠物"视频）

cold_start = True | 返回条数 = 4
1. [0.6092] 美食,家常菜   aff=0.474 pop=1.000 fresh=1.000 qual=0.457  3分钟搞定深夜食堂
2. [0.3269] 旅行,自驾     aff=0.000 pop=0.886 fresh=0.707 qual=0.436  川西自驾第7天
3. [0.3241] 健身,减脂     aff=0.000 pop=0.948 fresh=0.630 qual=0.400  新手减脂期的一周饮食
4. [0.2942] 读书,认知     aff=0.000 pop=0.850 fresh=0.561 qual=0.400  《人类简史》到底在讲什么
```

被点赞标签（美食）的内容以 `aff=0.474` 获得最高分并排到首位，其余 `aff=0` 内容按热度与新鲜度排序——**个性化链路端到端成立**。

### 测试过程中发现并修复的真实缺陷（均为产品代码缺陷，非测试自身问题）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | multipart 切分后误删 part 临时目录 | 大文件上传丢文件 | 修正临时目录生命周期归属 |
| 2 | 错误响应未排空请求体（HTTP/1.1 keep-alive） | 残留字节被当成下一个请求解析，连接错乱 | 增加排空逻辑 |
| 3 | **排空逻辑与已读请求体冲突** | 重复 handle 等"读体后报错"场景**永久死锁** | 引入 `_body_consumed` 状态标记 |
| 4 | **直接对 socket 调用 `read(65536)`** | keep-alive 下永远等不到 EOF，**所有上传请求挂死** | 引入 `LengthLimitedReader` 显式按 Content-Length 设界 |
| 5 | **召回配额乘以 feed size 裁剪候选池** | 小内容库 + 高行为用户下 feed 长度不足（6 条视频只召回 2 条） | 配额改为作用于候选池基准深度（200），设单路最小深度 20 |

第 3、4、5 项是**只有跑真实 HTTP 与真实数据才会暴露的缺陷**：单元测试用 `BytesIO`（`read()` 遇 EOF 返回短读）永远发现不了第 4 项；用小内容库跑不看返回条数就发现不了第 5 项。这三项已各自补上回归测试。

### 关于 R6：本心拍的控制面阻塞（需上层处理）

本心拍运行在 **未绑定任务的运行上下文**（`invocationSource=on_demand`、`contextIssueId=null`、`TMPDIR=paperclip-run-unassigned-*`）。因此对 PRO-1 的所有控制面写入均被 containment 层拒绝：

- `POST /api/issues/{id}/comments` → **403** `cross_issue_influence_run_context_required`
- `PATCH /api/issues/{id}` → **403**（同上）
- `POST /api/issues/{id}/recovery-actions/resolve` → **403**（同上）
- `POST /mcp/runtime-tools` → 「Connection requests require a task-bound heartbeat run」（同源问题）
- 官方 CLI `paperclipai issue comment`（`--run-id` 已带）→ **403**（同上）

唯一成功的是 `POST /api/issues/{id}/checkout`，它已把 PRO-1 从 `blocked` 置为 `in_progress` 并把 `checkoutRunId`/`executionRunId` 绑定到本运行 `8640ff78`。但该绑定**未**使后续写操作获得运行上下文。

**兜底处置**：PRO-1 存在一个 board 持有的活跃恢复动作（`missing_disposition`，owner=board，cause=`successful_run_missing_state`），其 `nextAction` 明确要求由 board 操作员选择合法处置。本心拍据此把交付物写入 Git 仓库（可持久、可审计），并以本运行的结果通道上报。**建议 board 将该议题以任务绑定的方式重新唤醒本 Agent**，届时即可正常落评论、开子议题与闭环状态。
