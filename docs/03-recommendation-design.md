## 1. 背景、目标与设计原则

### 1.1 产品背景

`short-video-platform` 是一个新立项的短视频平台。MVP 只做两件核心事：

- **视频上传**（生产者侧：创作者发布视频、打标签、生成封面/音频指纹）；
- **推荐流（recommendation feed）**（消费者侧：竖滑全屏信息流，单次请求返回 N 条候选并按序展示）。

MVP 的现实约束（决定了本方案的取舍）：

| 约束 | 现状 | 对算法设计的影响 |
| --- | --- | --- |
| 数据量小 | 冷启动期视频量 1e4~1e5，用户量 1e4~1e6 | 允许全量召回、小模型，无需工业级 ANN 也能跑 |
| 行为稀疏 | 大部分视频互动数为 0~个位数 | 必须先跑通热门/内容匹配，协同过滤只能做补充 |
| 团队小 | 无实时特征平台/无深度模型训练经验 | 基线用**线性加权 + 规则**，深水区（双塔/多任务）作为升级路径 |
| 冷启动严重 | 每天新增大量新用户、新视频 | 冷启动必须是一等公民（第 6 章） |
| 合规要求 | 内容安全、防信息茧房 | 重排层强制多样性与风控护栏 |

### 1.2 设计目标（可度量的）

| 目标 | 指标 | MVP 目标基线 |
| --- | --- | --- |
| 有货可推 | 单次请求有效候选数 | ≥ 500 |
| 相关 | 离线 Recall@100 | ≥ 0.55 |
| 有序 | 离线 NDCG@10 | ≥ 0.62 |
| 好看 | 在线完播率（完成/曝光） | ≥ 0.35 |
| 上瘾 | 人均日使用时长 | ≥ 18 分钟 |
| 留下 | 次日留存（D1） | ≥ 0.35 |
| 不崩坏 | 举报率 | ≤ 0.3%（护栏） |

### 1.3 设计原则

1. **漏斗分层（Funnel）**：召回负责“广”（Recall 优先），排序负责“准”（Precision 优先），
   重排负责“稳”（多样性与业务规则）。这与 YouTube / 抖音公开的两阶段（甚至多阶段）范式一致 [R1][R4]。
2. **先可用、再最优**：MVP 用可解释、可手算的线性模型上线，跑通数据闭环后再引入 GBDT/DNN。
3. **冷启动优先**：任何模块在特征缺失时都必须有明确降级路径，绝不允许“无候选可推”。
4. **多目标 + 护栏**：同时优化完播、互动、时长，并用举报率、跳过率、创作者集中度做护栏，
   避免单目标最优化带来的点击欺诈/信息茧房 [R4][R5]。
5. **可评测**：离线、在线、护栏三层指标齐备，任何改动都能被量化验证（第 8 章）。

## 2. 系统总体架构

### 2.1 流水线（Pipeline）

```
                        ┌──────────────────────────────────────────────┐
   user_id + 上下文 ───▶ │  ① 候选召回 Candidate Generation (约 500 条)  │
                        │   item-item CF │ 关注 │ 热门新鲜 │ 标签 │ 兜底 │
                        └───────────────────────┬──────────────────────┘
                                                ▼
                        ┌──────────────────────────────────────────────┐
                        │  ② 过滤 Filtering                             │
                        │   已曝光去重 │ 黑名单/风控 │ 地域/年龄 │ 断链    │
                        └───────────────────────┬──────────────────────┘
                                                ▼
                        ┌──────────────────────────────────────────────┐
                        │  ③ 排序 Ranking (约 200 条 → 打分)            │
                        │   线性基线 → {GBDT | Wide&Deep | 双塔}        │
                        └───────────────────────┬──────────────────────┘
                                                ▼
                        ┌──────────────────────────────────────────────┐
                        │  ④ 重排 Re-ranking                            │
                        │   MMR 多样性 │ 创作者打散 │ 新鲜度 │ ε-greedy  │
                        └───────────────────────┬──────────────────────┘
                                                ▼
                        ┌──────────────────────────────────────────────┐
                        │  ⑤ 曝光 Exposure (Top-N，一行 N≈10)           │
                        └───────────────────────┬──────────────────────┘
                                                ▼
                              用户行为日志 ──▶ 回流训练/评测 (闭环)
```

图示见 `docs/images/recsys-pipeline.svg`（含冷启动双塔路由）。

### 2.2 三级数据分层

| 层 | 延迟 | 用途 | 技术选型（MVP） |
| --- | --- | --- | --- |
| 离线 Offline | 小时/天 | 训练模型、计算 item-item 相似度、统计热门 | Spark / 单机 Pandas + Parquet |
| 近线 Nearline | 分钟 | 增量更新热度、新鲜度、创作者统计 | Kafka + Flink（MVP 可退化为定时任务） |
| 在线 Online | 毫秒 | 特征读取、打分、重排、返回 | Redis（特征/倒排）+ 无状态 Serving 服务 |

### 2.3 延迟预算（单次 feed 请求，P99）

| 阶段 | 预算 |
| --- | --- |
| 上下文拉取 + 用户特征 | 10 ms |
| 多路召回（并行） | 40 ms |
| 过滤 | 5 ms |
| 排序（200 条打分） | 30 ms |
| 重排 | 10 ms |
| 序列化 + 网络 | 15 ms |
| **合计** | **≤ 110 ms（含兜底重试 ≤ 200 ms）** |

### 2.4 服务接口（伪代码）

```python
def recommend_feed(user_id: str, ctx: Context, n: int = 10) -> list[Item]:
    feats  = feature_service.get(user_id, ctx)          # 用户+上下文特征
    cands  = recall(user_id, feats)                     # ① 多路召回
    cands  = filter_out(cands, user_id, ctx)            # ② 过滤
    scored = rank(cands, feats)                         # ③ 排序
    final  = rerank(scored, feats, n)                   # ④ 重排
    log_impressions(user_id, final, ctx)                # 曝光日志
    return final[:n]                                    # ⑤ 曝光
```

## 3. 候选召回（多路 Recall）

目标：在毫秒级、从全库（甚至未来百万级）中捞出 **500~1000** 条“大概率相关”的候选，
保证 **召回率（Recall）** 足够高。多路召回的核心思想是**并发跑多条互补策略**，
各自返回带分数的候选，再归一化融合去重。

### 3.1 召回路径总览与配额

单次请求总候选约 500 条，各路配额如下（配额可配置，按 A/B 调整）：

| 路 # | 召回路径 | 配额 | 适用用户 | 主要信号 |
| --- | --- | --- | --- | --- |
| R1 | item-item 协同过滤 | 150 | 有历史行为 | 共现相似度 |
| R2 | 创作者关注（社交） | 80 | 有关注 | 关注关系 + 时效 |
| R3 | 热门新鲜（Trending） | 120 | 全部 | 热度 × 时间衰减 |
| R4 | 标签内容匹配 | 100 | 有标签偏好 | 标签/embedding 相似 |
| R5 | 冷启动兜底 | 50 | 新用户/新视频 | 全局先验 + 多样性采样 |
| | **合计** | **500** | | |

### 3.2 R1：item-item 协同过滤

**思想**：用户看过的物品，与其“相似”的物品更可能被喜欢。MVP 采用 **item-based CF**（而非 user-based），
因为物品数远小于用户数、相似度矩阵可离线预计算且稳定。

**相似度定义**（三种，MVP 先用手工可算的 Jaccard，规模上来后切余弦/Swing）：

```
(余弦)  sim_cos(i, j) = (v_i · v_j) / (||v_i|| · ||v_j||)
(杰卡德) sim_jac(i, j) = |U_i ∩ U_j| / |U_i ∪ U_j|
(Swing)  sim_swing(i,j) = Σ_{u∈U_i∩U_j} Σ_{v∈U_i∩U_j, v≠u} 1 / (α + |I_u ∩ I_v|)
```

其中 `U_i` = 看过物品 i 的用户集合，`I_u` = 用户 u 看过的物品集合。
Swing 额外惩罚“大众爆款导致的虚假共现”，在长尾上更稳。

**打分**：对用户 u 的候选物品 i，

```
score_CF(u, i) = Σ_{j ∈ I_u} sim(i, j) · w(u, j)
```

`w(u, j)` 是用户 u 对历史物品 j 的权重（如 完播=1.0、点赞=1.5、划过=0），
可理解为软化的评分。这样避免了显式评分缺失的问题。

**数值示例（Jaccard）**：
```
U_{V1} = {u1, u2, u3, u5, u8}   (看过 V1 的 5 个用户)
U_{V2} = {u1, u3, u5, u9}       (看过 V2 的 4 个用户)
交集 |U_V1 ∩ U_V2| = |{u1,u3,u5}| = 3
并集 |U_V1 ∪ U_V2| = |{u1,u2,u3,u5,u8,u9}| = 6
sim_jac(V1, V2) = 3 / 6 = 0.5
```
若用户 u3 看过 V1（权重 1.0），未看过 V2，则 `score_CF(u3, V2) += 0.5 × 1.0 = 0.5`。

**工程要点**：
- 离线用共现矩阵 → Top-K 截断（每物品保留最相似 200 个）存 Redis / 本地 KV；
- 在线：读用户最近 M 条历史（M=50），对每条取邻居累加分数。复杂度 O(M·K)；
- 冷物品没邻居时自动落空，由兜底路补足。

### 3.3 R2：创作者关注（社交召回）

**思想**：用户显式关注的创作者发布的新内容，是最高优先级的候选。

```
score_follow(u, i) = 1{creator(i) ∈ Follow(u)} · freshness(i) · affinity(u, creator(i))
```

`follow_w` 可按互动频率加权：`affinity = log(1 + 与该创作者的互动次数) / log(1 + max_互动)`。

**数值示例**：
```
u1 关注 C1；V1 由 C1 发布，发布 2h 前（freshness 见 3.5 = 0.920）
affinity(u1, C1) = log(1+20)/log(1+100) = 3.045/4.615 = 0.660
score_follow(u1, V1) = 1 × 0.920 × 0.660 = 0.607
```

### 3.4 R3：热门新鲜（Trending）

**思想**：全局或分垂类（tag/地域/语言）的“当下热门”，解决协同过滤覆盖不到的新内容。
关键是**热度必须随时间衰减**，否则老爆款长期霸榜。

**公式（抖音/Hacker-News 风格时间衰减）**：

```
Hot(v, t) = (like + 2·comment + 3·share + 0.2·play) / (T_age_hours + 2)^α
```

- `α` 时间衰减指数，MVP 取 **1.5**（越大越偏向新鲜）；
- 分母 `+2` 做平滑，避免刚发布（age≈0）时除零爆炸；
- 分子权重体现行为价值：分享 > 评论 > 点赞 > 播放。

**数值示例**（V3：play=2000, like=300, comment=40, share=15, age=3h）：
```
分子 = 300 + 2×40 + 3×15 + 0.2×2000 = 300 + 80 + 45 + 400 = 825
分母 = (3 + 2)^1.5 = 5^1.5 = 11.180
Hot(V3) = 825 / 11.180 = 73.8
```
对比老爆款 V4（play=20000, like=800, comment=200, share=60, age=120h）：
```
分子 = 800 + 400 + 180 + 4000 = 5380
分母 = (120+2)^1.5 = 122^1.5 = 1347.6
Hot(V4) = 5380 / 1347.6 = 3.99    ← 远低于 V3
```
可见 V3 虽播放量仅为 V4 的 1/10，但“当下热度”高 18 倍——这正是新鲜度衰减的作用。

分垂类热门：把 Hot 按主标签分组各自排序取 Top-K，避免单一垂类霸榜。

### 3.5 R4：标签内容匹配

**思想**：基于内容属性（标签、音频、封面、文本标题）做内容相似度，无需行为数据即可工作，
是冷启动时期的主力。

**（a）标签向量（MVP 首选）**：把视频表示为其标签集合，用户表示为历史消费标签的
TF-IDF/时间衰减加权向量，用余弦相似度：

```
score_tag(u, i) = cos( P_u , T_i ) = (P_u · T_i) / (||P_u||·||T_i||)
P_u[tag] = Σ_{j ∈ I_u} w(u,j) · 1{tag ∈ T_j} · decay(age_j)
```

**数值示例**：
```
T_V3 = {宠物:1, 猫:1}
P_u2 = {宠物:2.0, 猫:1.5, 美食:0.3}   (u2 的历史偏好)
cos = (2.0×1 + 1.5×1 + 0×0) / (√(2.0²+1.5²+0.3²) × √(1²+1²))
    = 3.5 / (√6.34 × √2) = 3.5 / (2.518 × 1.414) = 3.5 / 3.561 = 0.983
```
→ V3 与 u2 标签高度匹配。

**（b）Embedding 向量（升级）**：用视频封面/前 3 秒画面 + 音频指纹 + 标题文本，经
多模态编码器得到 item embedding；多路召回即双向 **双塔 + ANN 检索**（见 4.5）。

### 3.6 R5：冷启动兜底

当上述任一路返回为空，或用户/物品极度稀疏时启用（详见第 6 章）：

- **新用户**：用注册地域/设备/首屏引导选择作为先验，走全局热门 + 探索性抽样；
- **新视频**：给一个“保底曝光池”，按创作者等级/标签均匀发牌（类似“流量池”机制）；
- **新品类**：若无任何标签匹配，则从全库按**最大边际相关（MMR）**做多样性采样。

### 3.7 多路融合（Fusion）

各路分数量纲不同，必须先归一化再加权融合：

```
score_recall(u, i) = Σ_{p ∈ Paths} α_p · norm_p( score_p(u, i) )      (i 不在该路则该项为 0)
norm_p(x) = (x - min_p) / (max_p - min_p)        或   norm_p(x) = x / (x + k_p)（类 sigmoid 平滑）
```

**路权重示例**（MVP 初值，按线上效果迭代）：

| 路 | α_p | 说明 |
| --- | --- | --- |
| R1 CF | 0.35 | 行为最可信 |
| R2 关注 | 0.30 | 强关系 |
| R3 热门 | 0.15 | 保证新鲜/覆盖 |
| R4 标签 | 0.15 | 内容兜底 |
| R5 冷启 | 0.05 | 探索种子 |

**数值示例（u1 对 V1）**：
```
norm_CF = 0（无 CF 路命中）        → 0.35 × 0 = 0
norm_follow = 0.607 / (0.607+1) = 0.378   → 0.30 × 0.378 = 0.113
norm_hot = 73.8 / (73.8+1) = 0.987        → 0.15 × 0.987 = 0.148
norm_tag: cos=1.0（美食完全匹配）→ 0.15 × 1.0 = 0.150
score_recall(u1, V1) = 0 + 0.113 + 0.148 + 0.150 = 0.411
```

融合后按分数截断 Top-500，进入阶段②过滤。

## 4. 排序模型（Ranking）

**目标**：把 500 条候选精排为 200 条，用**更多、更细的交叉特征**给出精准打分，
优化目标从“是否相关”升级为“用户价值最大化”。这一阶段可用全库召回时算不起的特征
（如用户×创作者的历史互动）[R1]。

### 4.1 特征清单

**用户侧（User features）**

| 特征 | 类型 | 说明/取值 |
| --- | --- | --- |
| u_activity | 数值 | 近 7 天活跃度（曝光数/登录天数） |
| u_tag_pref[tag] | 向量 | 各标签兴趣分（时间衰减加权历史） |
| u_avg_watch_ms | 数值 | 用户平均观看时长 |
| u_follow_cnt | 数值 | 关注数 |
| u_device / u_loc / u_lang | 类别 | 设备、地域、语言 |
| u_hist_len | 数值 | 历史行为条数（衡量冷度） |
| u_last_active_gap | 数值 | 距上次活跃间隔（小时） |

**物品侧（Item features）**

| 特征 | 类型 | 说明 |
| --- | --- | --- |
| i_age_hours | 数值 | 发布时长 |
| i_duration | 数值 | 视频时长（秒） |
| i_tag_vec | 向量 | 标签 one-hot/TF-IDF |
| i_embed | 向量 | 多模态 embedding（升级后） |
| i_ctr | 数值 | 曝光点击率（平滑后） |
| i_completion | 数值 | 完播率（平滑后） |
| i_like_rate / comment / share | 数值 | 互动率 |
| i_creator_id | 类别 | 创作者 |
| i_creator_grade | 数值 | 创作者等级/历史健康度 |
| i_report_rate | 数值 | 举报率（护栏输入） |

**上下文与交叉（Context / Cross features）**

| 特征 | 类型 | 说明 |
| --- | --- | --- |
| c_hour / c_weekday | 类别 | 请求时刻（时段偏好） |
| c_network / c_scene | 类别 | WiFi/4G、场景 |
| x_tag_match(u,i) | 数值 | 用户偏好与物品标签的余弦 |
| x_creator_affinity(u,i) | 数值 | 用户×创作者历史互动强度 |

### 4.2 线性加权基线打分公式（MVP 落地版）

MVP 采用**可解释、可手算、无需训练**的线性模型：

```
S(u, v) = w1·Aff(u,v) + w2·Pop(v) + w3·Fresh(v) + w4·Social(u,v) + w5·Qual(v) + b
```

| 权重 | 含义 | MVP 初值 | 取值范围 |
| --- | --- | --- | --- |
| w1 | 标签兴趣匹配度权重（个性化核心） | **0.45** | [0.3, 0.6] |
| w2 | 物品热度权重（社会认同） | **0.20** | [0.1, 0.3] |
| w3 | 新鲜度权重（时效） | **0.15** | [0.1, 0.25] |
| w4 | 社交/关注权重 | **0.10** | [0.05, 0.2] |
| w5 | 内容质量权重（完播/互动） | **0.10** | [0.05, 0.2] |
| b  | 偏置 | 0 | 可学习 |

各特征定义与归一化：

```
Aff(u,v)    = 标签兴趣匹配度 ∈ [0,1]      （见 3.5，余弦或加权命中率）
Pop(v)      = ln(1 + plays_v) / ln(1 + max_plays)          ∈ [0,1]
Fresh(v)    = exp( -age_hours / τ ),  τ = 24h              ∈ (0,1]
Social(u,v) = 1{creator(v) ∈ Follow(u)}                    ∈ {0,1}
Qual(v)     = completion_rate_v（平滑后）                   ∈ [0,1]
```

> **权重标定建议**：MVP 上线前用网格搜索（步长 0.05）在离线 NDCG@10 上粗调；
> 上线后用**逻辑回归**自动学习——把 S 经 sigmoid 映射为点击/完播概率，用历史曝光数据拟合
> w（等价于 LR 的系数），即完成“手工权重 → 数据驱动权重”的平滑过渡。

### 4.3 从打分到多目标（概率校准 + 价值权重）

线性打分只看排序，不区分行为类型。升级做法：分别预测 P(完播)、P(点赞)、P(评论)、P(分享)、P(关注)，
再用**行为价值权重**融合（这正是抖音公开的核心逻辑：“预测用户行为概率 × 行为价值权重”[R4]）：

```
E[Value](u,v) = Σ_b  β_b · P_b(u,v)
```

| 行为 b | 价值权重 β_b | 理由 |
| --- | --- | --- |
| 完播 complete | 1.0 | 基准，代表内容被消费 |
| 点赞 like | 0.7 | 弱正向 |
| 评论 comment | 0.9 | 强互动、社区价值 |
| 分享 share | 1.3 | 拉新，最高价值之一 |
| 关注 follow | 1.5 | 长期留存价值最高 |

**数值示例**：某视频预测为 P(完播)=0.55, P(点赞)=0.20, P(评论)=0.05, P(分享)=0.02, P(关注)=0.01。
```
E[Value] = 1.0×0.55 + 0.7×0.20 + 0.9×0.05 + 1.3×0.02 + 1.5×0.01
         = 0.55 + 0.14 + 0.045 + 0.026 + 0.015 = 0.776
```

**时长目标（YouTube 范式）**：若想优化“观看时长”而非“点击”，用**观看时长加权的逻辑回归**——
正样本（点击）按实际观看时长加权、负样本权重为 1，此时学习到的 odds ≈ 期望观看时长 [R1]。
这能有效抑制“标题党/点击欺诈”（高 CTR 低完播）。

### 4.4 升级路径（LR → GBDT → Wide&Deep → 双塔/多任务）

| 阶段 | 模型 | 训练成本 | 预期增益（NDCG@10） | 触发条件 |
| --- | --- | --- | --- | --- |
| P0 | **线性加权/规则**（4.2） | 无（手调） | 基线 0.62 | MVP Day-1 必须上线 |
| P1 | **逻辑回归 LR** | 极低 | +0.02~0.04 | 有 ≥ 1 周曝光日志 |
| P2 | **GBDT（LightGBM/XGBoost）** | 低（CPU 可训） | +0.05~0.08 | 特征上百、日志 ≥ 1e6 行 |
| P3 | **Wide&Deep / DeepFM** | 中（需 GPU） | +0.06~0.10 | 需捕捉高阶交叉 [R2] |
| P4 | **双塔召回 + 多任务排序（MMoE/ESMM）** | 高 | +0.08~0.15 | 千万级数据、有向量检索基建 [R1] |

**P2 GBDT 要点**：
- 目标：二分类（是否完播/点击）或排序（LambdaMART）；
- 特征离散化 + 分桶；处理缺失值天然友好；
- 输出概率可直接替代 4.3 里的 P_b。

**P3 Wide&Deep 要点** [R2]：
- Wide 部分记住（memorize）高频共现（如 用户地域×热门标签），Deep 部分泛化（generalize）；
- 联合训练：`P = sigmoid(w_wide·[x, φ(x)] + w_deep·a_last + b)`。

**P4 双塔/多任务要点** [R1]：
- **双塔召回**：用户塔吃用户+上下文特征，物品塔吃物品特征，分别输出 embedding，
  用内积/余弦作为匹配分；线上用 **FAISS/HNSW** 做 ANN 检索，把 O(N) 降到 O(log N) [R10]；
- **训练技巧（YouTube）**：极端多分类 + 负采样；引入 **example age 特征** 消除历史偏差、
  偏向新鲜内容（推理由时置 0）；用 **future-watch holdout** 而非随机划分，保留时间因果 [R1]；
- **多任务**：MMoE/ESMM 共享底层、独立塔输出多目标概率，缓解多目标冲突。

### 4.5 训练样本与标签设计

- **样本构造**：以“曝光”为粒度，曝光且完播=正样本；曝光但 2 秒内划过=强负样本；
  曝光未点击=弱负样本。
- **负采样**：正负比 1:4~1:10（双塔召回训练时用 in-batch negative）。
- **去偏**：位置偏差用位置特征/逆倾向加权（IPS）；时长偏差用观看时长加权。
- **时间划分**：训练用 T-7~T-1 天、验证用 T-1~T（严禁随机打乱时间）。

## 5. 重排（Re-ranking）

排序模型只对**单条物品**打独立分，会导致“全屏同类”“同一个创作者刷屏”，
且不解决探索、业务规则问题。重排层负责：多样性、打散、新鲜度、去重、探索-利用。

### 5.1 多样性：MMR（最大边际相关）

MMR 由 Carbonell & Goldstein (1998) 提出 [R3]，核心是“在相关性和新颖性之间取平衡”：

```
MMR = argmax_{i ∈ R \ S} [ λ · Rel(u, i)  −  (1 − λ) · max_{j ∈ S} Sim(i, j) ]
```

- `R` 候选集合，`S` 已选集，`Rel` 相关性（用第 4 章打分归一化），`Sim` 物品间相似度；
- `λ ∈ [0,1]` 平衡相关性与多样性：λ→1 退化为纯相关性排序，λ→0 追求最大差异；
- 推荐初值 **λ = 0.7**（略偏相关性），搜索/推荐场景常用区间 [0.6, 0.8]。

**数值示例（u1）**：候选〔V1=0.934, V2=0.827, V3=0.536, V5=0.514, V4=0.281〕，
相似度按标签 one-hot 计算：美食{V1,V2} 相似度=1，宠物{V3,V5} 相似度=1，跨标签=0。取 λ=0.7。

```
第 1 步：S 空 → 直接选最高 V1 (0.934)
第 2 步：候选 V2、V3
   V2: 0.7×0.827 − 0.3×sim(V2,V1)=0.7×0.827 − 0.3×1.0 = 0.5789 − 0.30 = 0.2789
   V3: 0.7×0.536 − 0.3×sim(V3,V1)=0.3752 − 0.3×0   = 0.3752   ← 胜出
   → 选 V3
第 3 步：候选 V2、V5、V4
   V2: 0.5789 − 0.3×max(sim(V2,V1)=1, sim(V2,V3)=0) = 0.2789   ← 胜出
   V5: 0.3598 − 0.3×max(0, 1) = 0.0598
   V4: 0.1967 − 0 = 0.1967
   → 选 V2
第 4 步：候选 V5、V4
   V5: 0.3598 − 0.3×1 = 0.0598
   V4: 0.1967           ← 胜出
   → 选 V4
第 5 步：选 V5
最终 MMR 序列：V1, V3, V2, V4, V5
```

对比“纯相关性排序”：`V1, V2, V3, V5, V4`。可见 MMR 把宠物视频 V3 提到了第 2 位，
避免了 V1、V2 两条同标签（同创作者）视频连排的“同质化”。

### 5.2 创作者打散（Creator diversification）

硬规则 + 软约束结合，简单高效：

- **滑动窗口硬约束**：同一个创作者的视频，任意相邻 `W=3` 个曝光位内不得出现 2 次；
- **全局配额**：单个创作者在全屏 N 条中占比 ≤ 30%（如 N=10 则 ≤ 3 条）；
- **同类目平滑**：同一主标签连续出现 ≤ 2 条。

实现：在 MMR 迭代中，对被约束的候选乘以惩罚因子（如 ×0.1）或直接从候选池剔除一轮。

### 5.3 新鲜度衰减（在重排层的二次施加）

排序层已有 Fresh 特征，重排层再做一次“位置级”衰减，保证同一请求内老内容不会占据高位：

```
Fresh_rerank(v) = exp( -age_hours(v) / τ2 ),  τ2 = 48h    ← 比排序层 τ=24h 更缓
S_final(v) = S_rank(v) · ( 1 + γ · Fresh_rerank(v) ),  γ = 0.2
```

**数值示例**：V4（age=120h）→ Fresh=exp(-2.5)=0.082，`S_final = 0.281 × (1+0.2×0.082)=0.286`；
V3（age=3h）→ Fresh=exp(-0.0625)=0.939，`S_final = 0.536 × 1.188 = 0.637`，进一步抬高新鲜内容。

### 5.4 去重

- **精确去重**：按 video_id 去重（历史已曝光 + 本次请求内）；
- **近似去重**：同一视频的转载/搬运，用 **SimHash / 感知哈希（pHash）** 对封面+音频指纹
  计算 64-bit 哈希，汉明距离 ≤ 3 视为重复，只保留热度最高的一条；
- **用户级疲劳控制**：同一视频对同一用户 7 天内不重复曝光（除非用户主动复看）。

### 5.5 探索-利用（Exploration vs Exploitation）

新视频/新创作者需要“破圈”机会，纯利用会让它们永远拿不到曝光（马太效应）。

**（a）ε-greedy（MVP 首选，实现最简单）**

```
以概率 (1−ε) 选择当前最优：  argmax_i S_final(i)
以概率 ε     随机探索：      从剩余候选中均匀/按标签采样
```
- ε 初值 **0.1**，随数据积累退火：`ε_t = max(0.02, ε_0 · 0.995^t)`（t 为天）；
- 探索位可固定放在第 4、7 位，保证不破坏头部体验。

**数值示例**：ε=0.1 时，第 4 个曝光位抛均匀随机数 r=0.07 < 0.1 → 触发探索，
从剩余候选中随机抽到 V5，则本次曝光序列由 `V1,V3,V2,V4,V5` 变为 `V1,V3,V2,V5,V4`。

**（b）Thompson Sampling（升级，长期收益更高）** [R7]

为每个视频维护完播率的 Beta 后验 `Beta(α_v, β_v)`，每次请求对每个候选采样 `θ_v ~ Beta(α_v, β_v)`，
取 `argmax θ_v`；曝光后按结果更新 `α_v += 完播数, β_v += 未完播数`。

```
α_v ← α_v + 1{完播},   β_v ← β_v + 1{曝光且未完播}
```
- 后验不确定度高（新视频）→ 采样方差大 → 自然获得更多探索机会；
- 后验收敛后自动减少探索，比固定 ε 更自适应。

**数值示例**：老爆款 V1 有 α=120, β=80（均值 0.600，标准差≈0.034）；
新视频 V5 有 α=2, β=2（均值 0.500，标准差≈0.224）。某次采样：
`θ_V1 = 0.612`、`θ_V5 = 0.688` → V5 胜出获得一次曝光机会（探索）。
多试几次后若 V5 真实完播率偏低，其 α/β 迅速收敛，不再挤占头部。

**（c）封顶探索（流量池/分层扶持）**：新视频进入“保底曝光池”，
在第 0 小时固定给予 500~1000 次曝光，按完播/互动表现决定是否升级到更大流量池（抖音式分层）。

### 5.6 重排伪代码

```python
def rerank(scored, feats, n, lam=0.7, eps=0.1, creator_cap=3, win=3):
    S, pool = [], list(scored)                     # pool: (item, S_final)
    while pool and len(S) < n:
        # (1) 创作者窗口打散：过滤掉违反窗口约束的
        cand = [x for x in pool if ok_creator_window(x, S, win, creator_cap)]
        if not cand: cand = pool                  # 兜底放开
        # (2) ε-greedy 探索
        if random() < eps:
            pick = random.choice(cand)
        else:
            # (3) MMR 选点
            pick = max(cand, key=lambda x: lam*x.score - (1-lam)*max_sim(x, S))
        S.append(pick); pool.remove(pick)
    return S
```

## 6. 冷启动方案

冷启动是短视频平台的生死线：每天都有大量**新用户**和**新视频**。原则是
“**先给合理默认，再用行为快速纠偏**”。

### 6.1 新用户冷启动

| 阶段 | 策略 | 具体做法 |
| --- | --- | --- |
| 0 次行为 | 全局先验 | 地域/语言/设备 + 全站分垂类热门，多样性 > 个性化 |
| 1~3 次行为 | 快速纠偏 | 用首屏点击/完播更新标签偏好，权重大（学习率 η 大） |
| 4~10 次 | 混合召回 | 加入标签内容匹配 + 轻量 CF |
| >10 次 | 正常个性化 | 进入标准流水线 |

**新用户首屏配额示例（N=10）**：

```
3 条 全局最热（保证“不难看”）
3 条 分垂类热门（美食/宠物/科技 各 1，保证多样性）
2 条 探索（ε 提高为 0.3，加速兴趣探测）
2 条 高互动率长尾（提升内容多样性、扶持创作者）
```

**快速纠偏公式**（新用户偏好更新，η 大）：
```
P_u[tag] ← (1−η)·P_u[tag] + η·1{tag ∈ T_consumed},   η_新用户 = 0.5（老用户 η = 0.1）
```

### 6.2 新视频冷启动

- **保底流量池**：新视频发布后 0~2h 进入探索池，固定曝光 500~1000 次；
- **初始特征**：用创作者历史完播率 + 标签/embedding 相似视频的表现作为先验预测（内容相似迁移）；
- **晋级机制**：池内完播率 > 同垂类中位数 → 升级到更大池；否则衰减下线；
- **反作弊**：识别刷量，异常互动不计入热度。

**新视频初始质量先验**：
```
Qual_new(v) = 0.5 · Qual(creator) + 0.5 · mean( Qual(相似视频) )
```
示例：创作者历史完播 0.6，同标签相似视频平均 0.5 → `Qual_new = 0.5×0.6 + 0.5×0.5 = 0.55`。

### 6.3 新品类/新垂类冷启动

- 标签/embedding 无邻居时，走**MMR 多样性采样**从全库抽取；
- 设置“新品类扶持位”（如每 20 次曝光留 1 个位置给低曝光垂类）；
- 监控垂类覆盖度（覆盖率 = 被曝光过的垂类数 / 总垂类数），低于阈值时加大对探索的投入。

**最终曝光：V1, V3, V2, V5, V4**

### 7.6 步骤 5：离线指标计算（以 U1 为例）

设 held-out 真实相关度（完播/点赞分级）：`V1=3, V3=3, V5=2, V2=1, V4=0`。

**NDCG@5**

理想排序（按相关度降序）`[V1,V3,V5,V2,V4]`：
```
IDCG = 3/1 + 3/1.585 + 2/2 + 1/2.322 + 0 = 3 + 1.893 + 1.000 + 0.431 = 6.323
```

纯相关排序 `[V1,V2,V3,V5,V4]`，相关度 `[3,1,3,2,0]`：
```
DCG  = 3/1 + 1/1.585 + 3/2 + 2/2.322 + 0 = 3 + 0.631 + 1.500 + 0.861 = 5.992
NDCG = 5.992 / 6.323 = 0.948
```

MMR 序列 `[V1,V3,V2,V4,V5]`，相关度 `[3,3,1,0,2]`：
```
DCG  = 3/1 + 3/1.585 + 1/2 + 0 + 2/2.585 = 3 + 1.893 + 0.500 + 0 + 0.774 = 6.166
NDCG = 6.166 / 6.323 = 0.975    ← 本样本中多样性重排反而提升了 NDCG
```

**AUC**（以 U1 打分，正样本={V1,V3}，负样本={V2,V4,V5}）
```
正负对比较（正样本分是否高于负样本）:
 V1(0.934) vs V2(0.827) → 1   V1 vs V4(0.281) → 1   V1 vs V5(0.514) → 1
 V3(0.536) vs V2(0.827) → 0   V3 vs V4 → 1          V3 vs V5(0.514) → 1
AUC = (1+1+1+0+1+1) / 6 = 5/6 = 0.833
```

**Recall@3**（相关集合={V1,V3,V5}）
```
Top-3 = {V1,V3,V2}，命中 {V1,V3} → Recall@3 = 2/3 = 0.667
```

**创作者集中度（Gini）**。设某日曝光份额 `C1=60%, C2=30%, C3=10%`：
```
G = ΣΣ|x_i−x_j| / (2·n²·μ)
  = (|60-30|+|60-10|+|30-10|)×2 / (2 × 9 × 33.33)
  = (30+50+20)×2 / 600 = 200 / 600 = 0.333
```
G=0.333 表示创作者曝光中度集中，需监控；G>0.5 触发多样性干预（加大探索、创作者打散）。

### 7.7 演示小结

| 阶段 | U1 结果 |
| --- | --- |
| 召回（融合后） | {V1,V2,V3,V4,V5} 全命中 |
| 线性排序 | V1,V2,V3,V5,V4 |
| MMR 重排 | V1,V3,V2,V4,V5 |
| ε-greedy 曝光 | **V1,V3,V2,V5,V4** |
| 离线指标 | NDCG@5=0.975，AUC=0.833，Recall@3=0.667 |

## 8. 评测体系

三层指标缺一不可：**离线快验证、在线真效果、护栏防崩坏**。

### 8.1 离线指标（Offline）

| 指标 | 公式 | 说明 | MVP 目标 |
| --- | --- | --- | --- |
| Recall@K | `Σ_u \|Rel_u ∩ TopK_u\| / \|Rel_u\| / \|U\|` | 召回覆盖能力，看召回层 | ≥ 0.55 (K=100) |
| NDCG@K | `DCG@K / IDCG@K`，`DCG=Σ rel_i/log2(i+1)` | 排序质量（位置敏感）[R6] | ≥ 0.62 (K=10) |
| AUC | `P(score_pos > score_neg)` | 二分类区分度，看排序层 | ≥ 0.72 |
| Precision@K | `\|Rel∩TopK\| / K` | 精确率 | ≥ 0.35 |
| 覆盖率 | `被推荐过的物品数 / 总物品数` | 长尾健康度 | ≥ 0.40 |
| 新颖性 | `mean(-log2(流行度))` | 推荐是否够“新” | 监控 |

离线评估注意：必须**按时间切分**（不能随机划分），并警惕“离线涨、在线跌”（见 8.4）。

### 8.2 在线指标（Online）

| 指标 | 定义 | MVP 目标 | 意义 |
| --- | --- | --- | --- |
| 完播率 | 完播数 / 曝光数 | ≥ 0.35 | 内容质量核心 |
| 人均使用时长 | 总观看时长 / DAU | ≥ 18 min | 平台粘性 |
| 次日留存 D1 | 次日回访 / 当日新增 | ≥ 0.35 | 长期价值 |
| 互动率 | (点赞+评论+分享) / 曝光 | ≥ 0.06 | 社区活跃 |
| CTR | 点击 / 曝光 | ≥ 0.55（竖滑自动播） | 首屏吸引力 |
| 人均播放数 | 播放数 / DAU | ≥ 40 | 消费深度 |

### 8.3 护栏指标（Guardrail / 反指标）

超越阈值必须触发告警并回滚，这是防“指标好看但生态崩坏”的关键 [R4][R5]。

| 护栏 | 定义 | 阈值 | 超标动作 |
| --- | --- | --- | --- |
| 举报率 | 举报数 / 曝光数 | > 0.3% | 回滚 + 内容复审 |
| 跳过率 | <2s 划过 / 曝光数 | > 0.55 | 排序质量告警 |
| 快速退出率 | App 打开后 <10s 退出 | > 0.25 | 首屏策略排查 |
| 创作者集中度 | 曝光份额 Gini 系数 | > 0.5 | 加大多样性/探索 |
| 新视频曝光占比 | 新视频曝光 / 总曝光 | < 0.10 | 提高冷启动配额 |
| 垂类覆盖度 | 被曝光垂类 / 总垂类 | < 0.6 | 提升探索 ε |
| 负反馈率 | 不感兴趣 / 曝光 | > 0.02 | 特征/召回排查 |

**Gini 系数公式**：
```
G = Σ_{i=1}^{n} Σ_{j=1}^{n} |x_i − x_j| / (2 · n² · μ)
```
（x_i 为第 i 个创作者的曝光量，μ 为均值；G=0 完全平均，G→1 极度集中。）

### 8.4 在线实验方法

- **A/B 实验**：按 user_id 哈希分桶（如 mod 100 → A:0-49, B:50-99），保证同用户一致；
- **样本量**：以完播率为核心指标，按 MDE=1%、α=0.05、power=0.8 估算需 ~2 万用户/组；
- **最小可观测量**：每变体至少跑满 1 个完整周（消除工作日/周末效应）；
- **长期 vs 短期**：短期 CTR 可能牺牲长期留存，需看 7 日/14 日留存与护栏指标；
- **离线在线不一致排查**：检查特征穿越（用了未来信息）、曝光偏差（未建模位置）、
  指标与业务目标的错位。

## 9. 工业实践 Trade-offs

下表汇总本方案在关键取舍上的选择与依据。

| 维度 | 方案 A | 方案 B | 取舍结论（MVP 选择） | 依据/理由 |
| --- | --- | --- | --- | --- |
| **热门 vs 个性化** | 纯热门（Top 播放） | 个性化（多路召回+排序） | **A 起步 → B 主导**：冷启动期热门保底，行为积累后个性化 | 纯热门完播率天花板低、创作者集中；但冷启动无行为时个性化无从谈起 |
| **实时特征 vs 批量特征** | 实时（Kafka+Flink，秒级） | 批量（T+1 离线） | **批量为主 + 关键实时**（热度、疲劳、在线计数） | 实时特征增益有限但成本高、易穿越；MVP 用 Redis 存近线可更新特征即可 |
| **探索 vs 利用** | 利用（ε=0，全推最优） | 探索（ε>0 / TS） | **低探索起步**（ε=0.1，退火到 0.02），长期切 TS | 纯利用致马太效应、新内容饿死；纯探索伤体验，需平衡 |
| **单目标 vs 多目标** | 单目标（只优化 CTR） | 多目标（完播+互动+时长+留存） | **多目标加权**，核心完播，分享/关注高价值 | 单目标 CTR 诱发标题党/点击欺诈；多目标 + 价值权重更贴合业务 [R4] |
| **模型复杂度** | 线性/规则（可解释） | DNN 双塔/多任务（高收益） | **线性上线 → GBDT → DNN 渐进** | MVP 先跑通闭环；深度模型需数据量与基建支撑，过早投入 ROI 低 |
| **召回策略** | 单路（CF） | 多路融合 | **多路融合**（5 路） | 单一策略覆盖不全、易同质；多路互补提升 Recall、支持冷启动 |
| **相似度度量** | Jaccard（简单） | Swing / 余弦 embedding | **Jaccard 起步 → Swing/双塔** | 早期行为稀疏，复杂度量优势不明显；数据充足后切换 |
| **重排多样性** | 纯相关性（λ=1） | MMR + 打散（λ=0.7） | **MMR + 创作者打散** | 纯相关性导致同质化、信息茧房；多样性提升长期留存 |
| **延迟 vs 精度** | 极低延迟（牺牲精度） | 高精度（允许更慢） | **分阶段预算**：召回粗、排序精、P99≤110ms | 短视频信息流对卡顿极敏感，必须卡死延迟预算 |

## 10. 工程实现要点

### 10.1 存储与数据结构

| 组件 | 选型 | 用途 |
| --- | --- | --- |
| 特征存储 | Redis（Hash）+ 本地 LRU 缓存 | 用户/物品/上下文实时特征，读写 <1ms |
| item-item 倒排 | Redis ZSET（key=video_id，member=邻居，score=相似度） | CF 在线查邻居 |
| 标签倒排 | Redis ZSET / 本地倒排索引 | 标签内容召回 |
| 热门榜单 | Redis ZSET（key=tag，score=Hot） | 分垂类热门，定时刷新 |
| 向量检索 | FAISS / Milvus（HNSW 索引） | 双塔召回阶段 ANN [R10] |
| 曝光/行为日志 | Kafka → 数据湖（Parquet） | 训练与离线评测 |
| 模型 | 线性（配置文件）/ LightGBM（PMML/ONNX）/ TorchServe | 排序打分 |

### 10.2 关键工程细节

1. **降级与超时**：每一路召回独立超时（15ms），超时/异常即跳过，保证整链路可用；
   最终结果不足 N 条时用全局热门补齐。
2. **一致性**：特征版本与模型版本绑定，避免“新特征喂给旧模型”。
3. **离线/在线一致性**：同一套特征计算逻辑（Feature-as-Code），防止训练-推理不一致。
4. **冷启动缓存**：新用户结果可预生成；热门榜单每 5 分钟刷新一次。
5. **监控告警**：QPS、P99 延迟、各路召回命中率、空结果率、护栏指标实时看板。

### 10.3 迭代里程碑

| 阶段 | 时间 | 交付 |
| --- | --- | --- |
| M0 | 第 1-2 周 | 逻辑链跑通：热门召回 + 线性排序 + 规则重排（本方案 P0） |
| M1 | 第 3-4 周 | 多路召回（+CF/标签/关注）+ 曝光日志闭环 + 离线评测 |
| M2 | 第 5-8 周 | LR/GBDT 排序 + MMR 重排 + 冷启动流量池 + A/B 平台 |
| M3 | 第 9-12 周 | 双塔召回 + 多任务排序 + 实时/近线特征 + 多目标融合 |

## 11. 风险与开放问题

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 行为数据稀疏 | CF/深度模型效果差 | 以内容匹配与热门为主，冷启动优先 |
| 信息茧房 | 用户流失、监管风险 | 强制多样性重排 + 长期留存指标 + 探索 |
| 冷启动曝光分配不公 | 创作者流失 | 流量池分层 + Gini 护栏 + 新视频保底 |
| 离线在线不一致 | 优化跑偏 | 时间切分、特征一致性、护栏兜底 |
| 延迟超标 | 体验崩坏 | 分阶段预算 + 超时降级 + 缓存 |
| 刷量作弊 | 热门榜单失真 | 反作弊规则 + 异常检测，异常互动不计入 |

**开放问题**：
1. 双塔 embedding 的模态融合（画面/音频/文本）如何权衡权重？
2. 多目标如何动态调整 β 权重以适应不同用户阶段（新用户更重多样、老用户更重兴趣）？
3. 长视频与短视频是否共用一套模型（MMOE 任务冲突）？
4. 隐私合规下如何做跨端特征（联邦学习/端上特征）？
